## F1: the cluster atom is not atomic

`\X` is translated as the TR29 alternation
(`Parser.graphemeClusterAtom`). Its residual branch is
`Prepend* [core] (Extend | ZWJ | SpacingMark)*`, and an orphan Extend or
ZWJ may serve as a core. Under leftmost-first semantics that star gives
back: `\X\X` on `e\u0301` takes the whole cluster first, fails the second
`\X`, and settles for `[e][U+0301]`. java's `XGrapheme` is a one-shot
`Grapheme.nextBoundary` scan — one cluster, never re-entered.

| pattern | input | JDK 26.0.2 | engine, both tiers |
|---|---|---|---|
| `\X\X` | `e\u0301` | no match | `0..2` |
| `\X\X\X` | `a\u200Db` | no match | `0..3` |
| `\X\X\b{g}` | `e\u0301\u0327` | no match | `0..3` |

It is the largest class: probes I 150, R 42, F 10. The shrinker's minimal
form is `\X\X` on `\u0301\u0327`. `\X\X` over `ab` is at parity — the gap
is the give-back, nothing else.

**Fix.** Wrap the translation in the engine's existing atomic construct
(the `(?>…)` fork rule — determinizer-level, no walker change). Spelled
through the public syntax it clears every witness above, keeps the controls
matching (`(?>\X)(?>\X)` over `ab`, `(?>\X)+` over `a\u0301\u0327x`), and
flattens the compile cost of F8:

| plain shape | plain | atomic spelling | atomic |
|---|---|---|---|
| `\X\X\X` | 95 ms | `(?>\X)(?>\X)(?>\X)` | 18–23 ms |
| `\X\X\X\X` | reject | four `(?>\X)` | 33–39 ms |
| `\X{1,4}` | reject | `(?>\X){1,4}` | 28–31 ms |
| `(a\|\X)+` | reject | `(?>(?:a\|\X))+` | 13 ms |
| `\X\X{2,}` | 138 ms | `(?>\X)(?>\X){2,}` | 31–34 ms |

(warm compile, library-default budget, this machine). This is a
public-syntax prototype, not a landed fix: the change belongs in the
parser, and the cluster battery rides both tiers.

## F2: two break-class readers

The JDK does not read `GraphemeBreakProperty.txt`. `Grapheme.getType`
derives the break class from the runtime general category: surrogates and
every unassigned code point (U+0378 alone excepted) become `Control`, a
spacing mark stays `SpacingMark` even where the data file says `Extend`.
The engine reads the 17.0 tables, where all of those are unlisted —
`Other`. A lone surrogate followed by a skin-tone modifier is two clusters
in java and one in the engine.

| pattern | input | JDK | engine |
|---|---|---|---|
| `\X` | `\uDC68\ud83c\udffb` | `[0..1, 1..3]` | `[0..3]` |
| `\b{g}` | `a\uDC68\ud83c\udffbb` | boundaries `0 1 2 4 5` | `0 1 4 5` |
| `\X`, `find(4)` | `abc\uD83D\uDC68\ud83c\udffbcd` | `4..5` | `4..7` |

All 44 records are surrogate-driven. A census over all 1 114 112 code
points (the JDK's `getType` against the engine's tables) gives the whole
gap:

| JDK class → engine class | code points | who is right |
|---|---:|---|
| `Control` → `Other` | 809 507 | unassigned — the **standard** is `Other` |
| `Control` → `Other` | 2 048 | surrogates — unlisted in the data; java's own choice |
| `SpacingMark` → `Extend` | 61 | U+09BE … U+1D172: the data file says `Extend`; both join, harmless |
| `SpacingMark` → `Other` | 2 | U+11720, U+11721: the **engine** is right (JDK-8394801) |

On unassigned code points the engine is conformant and the oracle is not.
UAX #29's summary list makes `Control` of unassigned code points **and**
Default_Ignorable ones; the 17.0 data file pre-lists all 3 769 of those as
`Control`, and the engine agrees with java on every one. None is in the
bucket — it is ordinary unassigned code points, which the data file defaults
to `Other` and the conformance test treats so (`÷ 0378 × 0308 ÷` is a
row). The JDK's classifier special-cases U+0378 to pass that row and types
every other unassigned code point `Control` (witness: `\X` on
`\u0379\u0301` — two clusters in java, one in the engine). On surrogates
the data file leaves them at its `Other` default and the conformance test
has none; java breaks after them.

**Decision.** `\X` and `\b{g}` need one classifier, and the lane needs a
reading. Recommended: the JDK's reading on the jur lane — the lane's
contract is `java.util.regex` parity and `\b{g}` already landed as "java's
own operational reading" — with the normative tables kept for pinned-version
providers and the re2j lane, and the delta pinned as the table above so the
choice can be flipped. The alternative, keeping UAX #29 and classifying the
oracle's deviations as known divergences, needs the predicate "input holds a
surrogate or an unassigned code point" — true for 996 of this run's 2 014
records, far too wide to hide real findings behind. The U+11720/U+11721
cells are the JDK's acknowledged bug and should not be mirrored.

Related, not seen in this run: the 26.0.2 `Grapheme.nextBoundary` never
updates its GB11 state (the update branch is dead code), so `\X` on
`👍 ZWJ ZWJ 👍` is one cluster in java and two in the engine — the engine
is right, and the JDK has fixed it for 28 (JDK-8393247). A known-oracle
cell to add before it surfaces.

## F3: the grapheme boundary under a region

Three mechanisms behind 223 `REGION_MISMATCH` records:

- **Origin un-rebased (176 records, 31 patterns).** The default-bounds
  combos are served through a `subSequence` view, and
  `Matcher.rebaseGBaseForView` shifts the `\G` base into view coordinates
  but not `scratch.gbOrigin`. `\b{g}` then scans from an absolute origin
  read as a view index: in a 4-unit view an origin of 7 is past the end, so
  every interior position reads "before the next boundary". `\b{g}` with
  `region(1,4)` on `abcd`: JDK iterates `1..1 2..2 3..3 4..4`, the engine
  `1..1 3..3 4..4`.
- **Wrong flag for the base pair (38 records, 21 patterns).** java's
  `GraphemeBound` takes its start/end index from `transparentBounds` (the
  region edges when opaque, the text edges when transparent); the engine
  keys them on the anchor bases, which follow `anchoringBounds`. The two
  disagree in exactly two combos, as mirror images — `\b{g}` on
  `e\u0301xy` with `region(1,4)`:

  | bounds | JDK | engine |
  |---|---|---|
  | anchoring off, opaque | `F=1..1` | `F=2..2` |
  | anchoring on, transparent | `F=2..2` | `F=1..1` |

  Whether java's choice of flag is intended is one of the open questions
  under JDK-8394894; parity says mirror it either way, pinned.
- **`\X` past the region end (9 records, 6 patterns) — the JDK's.**
  `XGrapheme` only checks `i < to`, then lets `nextBoundary` finish the
  cluster: `\X` with `region(0,1)` on a pair-cut input matches `0..2` in
  java, two units past the region. The engine finds nothing. The JDK
  maintainer called this "clearly a bug" (JDK-8394894, open). Treat it as a
  known-oracle cell; do not mirror.

## F4: grapheme-boundary scans are quadratic

Every `\b{g}` (and `\G`) artifact is routed away from the search ladder
into `runGeneric`'s restart-per-position walk (`TdfaRunner.match`): no
SearchDfa memo, no kill-point windows, no rung budgets. A start position
whose body can run wide walks to the end of input, so a no-match scan is
quadratic. All 12 `HANG_ENGINE` records sit there, 9.3–9.9 s of CPU each,
on the fuzzer's stretched (~4 300-char) probes.

| pattern | `find()` at 4 300 chars, no match | growth per doubling |
|---|---:|---|
| `\b.{2,}9` (control: the ladder) | 0.75 ms | linear |
| `\b{g}.{2,}9` | 73 ms | ×2.8 ×3.7 ×4.5 |
| `\X{2,}9` | 0.47 ms | linear (the JDK itself: 80 ms) |
| `\b{g}\X{2,}\b{g}9` | 1 246 ms | ×2.4 ×4.0 ×4.0 ×4.6 |

A bare `\b{g}z` scan stays linear (0.61 ms at 4 000 chars): each failed
start dies at once. The tax is the boundary plus a wide body. The soak's
replay pass called 9 of the 12 seeds slow-but-complete (13–33 s wall) and 3
clean; the wall includes gradle start and the shrinker, so the table above
is the measurement.

Results are correct; the cost is not bounded the way the rest of the engine
is. At the measured growth a 10 000-character input takes seconds
(extrapolated).

## F5: the last-scratch leak

`\b{g}` reads `matcher.last` as its scan origin, and java's quantifier
nodes use the same field as position scratch: `Ques.match` and
`Curly.match0` chain through `matcher.last` after each atom, and a failed
attempt leaves the stale value behind across start positions. The result is
a boundary that is false exactly where a cluster boundary is:

| pattern | input | JDK | engine |
|---|---|---|---|
| `\X?\b{g}` | `ab` | `F=0..0`, then `1..2` | `F=0..1`, then `1..1 2..2` |
| `a?\b{g}` | `aZ` | `F=0..0`, then `1..1 2..2` | `F=0..1`, then `2..2` |
| `\b{g}\X?z` | `aaz` | `F=2..3` | `F=1..3` |

`a?\b{g}` is the shrinker's own reduction of this class: no `\X` involved,
any quantified atom before or after the boundary does it. The word-boundary
control `a?\b` on `aZ` is at parity.

This is the "one documented divergence" of `jur-api-parity.md` (`(?:\b{g}a)+`
on `aa`), wider than it was written down. The engine serves the principled
reading. Upstream now agrees that reading is the right one: JDK-8396961,
"Pattern incorrect backtracking with grapheme cluster boundary" (filed
2026-11-24, open) reports the same wrong answer for `.?\b{g}b` on `ab`.

So these 112 records are not engine defects — but they are unclassified,
and they are the loudest signal on the lane after F1.

## F6: the oracle throws

`Pattern.compile("\\X*\\b{g}9").matcher("a9").find()` throws on the stock
JDK 26.0.1 and 26.0.2, from `find()`, `matches()` and `lookingAt()` alike:

```
java.lang.StringIndexOutOfBoundsException: Index 2 out of bounds for length 2
    at java.base/java.lang.Character.codePointAt(Character.java:9743)
    at java.base/jdk.internal.util.regex.Grapheme.nextBoundary(Grapheme.java:49)
    at java.base/java.util.regex.Pattern$GraphemeBound.match(Pattern.java:4227)
    at java.base/java.util.regex.Pattern$Curly.match0(Pattern.java:4586)
    at java.base/java.util.regex.Pattern$Curly.match(Pattern.java:4548)
    at java.base/java.util.regex.Pattern$Start.match(Pattern.java:3794)
    at java.base/java.util.regex.Matcher.search(Matcher.java:1765)
    at java.base/java.util.regex.Matcher.find(Matcher.java:785)
```

`nextBoundary` calls `codePointAt(src, off)` before testing `off < limit`;
a quantified `\X` that has consumed to the end leaves `matcher.last` equal
to the text length, and the `\b{g}` evaluated on the way back out hands
that to the scan. Same root as F5, one step further: also `\X+\b{g}z` on
`aa`, `\X?\b{g}9` on `aa`, `\b{g}\X*z` on `aa`. JDK-8396961 carries the
`Ques` form; the `Curly` forms here are worth adding to that report.

The engine does not throw: `\X*\b{g}9` on `a9` is `0..2` on both tiers.
Every `oracle-threw` record of this run (32 patterns) is this exception,
not the backtracker stack overflow the class was written for — and on those
120 cases the engine's answer was never compared with an oracle, only with
itself.

## F7: the fuzzer files budget rejects as unsupported

`jurLaneDomain` returns `graphemes-unsupported` whenever a pattern with a
grapheme construct is rejected by both tiers. Before #196 that meant a
syntax rejection. #196 noted that the guard "already handles" a compiled
`\X` — it handles a syntax rejection, not a budget one: since `\X`
compiles, a compile-budget rejection starts with `<reject` too, and the
predicate swallows it. All 120 records of that class, and 190 of the last
chunk's 85 848 cases (0.22 %) — twice the chunk's counted `BUDGET_REJECT`
class.

So the lane's budget rate is understated about threefold, and `\X`'s
compile cost (F8) has been invisible since the family landed. The fix is
one condition: the skip wants a syntax rejection. The stale "rejected
loudly" wording lives on in three places — the classifier's comment, the
fuzzer's class doc, and the grapheme paragraph of `jur-api-parity.md`.

## F8: quantified cluster atoms and the compile budget

At the soak's 8 M-tick scope, 14 distinct quantified-`\X` patterns
rejected in fifteen minutes (`\X{1,4}`, `\X{2,3}\b{g}`, `\X\b{g}\X`, …).
At the library default the cost is what a user sees:

| shape | compile | note |
|---|---:|---|
| `\X` | 6 ms | JDK: under 0.1 ms |
| `\X\X` → `\X\X\X` | 28 → 95 ms | ×3.5 per extra atom |
| `\X\X\X\X`, `\X{1,4}` | reject | "whole-match divergence exceeds the compile budget" |
| `(a\|\X)+` | reject | CFG edge cap: 4 195 988 successor arcs over 4 194 304 |
| `\b{g}\X{2,4}\Xb` | 280–320 ms | |

The atomic wrapper flattens that growth (second table under F1), which
points at the same non-atomicity as F1: every give-back interleaving with
the continuation is another DFA state. What remains afterwards is 15–40 ms
per `\X`-carrying compile, still hundreds of times the JDK's — a separate,
smaller item.

## Limits of this triage

Fifteen minutes, not a night: rates here are a slice, not README evidence.
Whole-run per-kind totals are lower bounds (see "The run"). The mechanism
split is a text classification over capped records, validated on
representatives rather than on all 606. Outside the harness, a standalone
probe diverges from the stock JDK on 26 inputs — the witnesses above, the
census corners, the GB11 shapes — with both tiers agreeing on every one,
and sits at parity on 14 controls. E2–E5 are root causes by inspection plus
witness, not prototyped fixes — only E1 was prototyped, through the public
`(?>…)` spelling. The upstream issue states are as of 2026-11-25.
